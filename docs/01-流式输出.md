# 流式输出（SSE）实现要点

## 为什么用 SSE 而不是 WebSocket

对话是单向流式：客户端发一次请求，服务端持续推送 token。天然符合 HTTP 语义，
不需要双工，所以用 SSE。

但没有用浏览器内置的 EventSource，原因是它有两个硬限制：
不支持 POST 方法、不能携带自定义请求头（比如鉴权 token）。
所以改用 fetch + ReadableStream 自己解析事件流。

## 事件协议设计

服务端自定义五种事件，每帧格式为 `event: 名称` 加 `data: JSON` 加一个空行：

- start：返回 traceId 与模型名
- delta：返回增量文本
- usage：返回 promptTokens 与 completionTokens
- done：正常结束
- error：异常结束

为什么要区分 done 和 error，而不是靠连接关闭判断结束：
连接断开既可能是正常完成，也可能是网络中断或服务端崩溃。
只靠关闭事件无法区分这三种情况，前端会错误地把失败当成成功。

## 前端解帧的三个坑

第一，不能假设一次 read 拿到完整帧。网络分包会导致一帧被切成两次到达，
所以要用缓冲区累积，再按双换行符切分，剩下的留到下次。

第二，TextDecoder 必须传 `{ stream: true }`。
中文字符在 UTF-8 里占三个字节，如果正好被切在两次读取之间，
不加这个参数会解出乱码。

第三，解码后要按块渲染 Markdown，而不是整段重渲染。
否则每个 token 都会触发全文重新解析，长回答时明显卡顿。

## 中断为什么要三层透传

用户点「停止生成」时，中断信号必须传到最底层，否则服务端会继续调用模型，
费用继续产生。

链路是三层：前端的 AbortController 触发 abort，
浏览器把中断转成后端的 request.signal，
后端必须把这个 signal 再传给模型 SDK 的请求参数。

少了最后一层，前端看起来已经停止，但服务端还在跑，账单还在涨。
