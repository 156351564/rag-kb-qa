# Token 成本核算

## 单价必须来自真实账单

不要用网上的报价，也不要凭印象写死。做法是：跑一批固定请求，
记录 token 数量，再和账单金额对照，反推出单价。

实测 DeepSeek 官方接口按每 token 计价：
标准档输入 2e-6 元，缓存命中输入 4e-8 元，输出 8e-6 元。
优惠时段价格正好是标准档的一半。

注意这三个价格必须放进一张表里驱动计算，不能散落在代码各处。
一旦供应商调价，散落的硬编码会漏改。

## 缓存命中是成本的大头

DeepSeek 支持前缀缓存：如果多次请求的开头部分相同（比如同一段系统提示词），
这部分输入按缓存价计费，价格只有标准输入的五十分之一。

实测在 Function Calling 场景下，前缀复用率高，缓存命中率能达到百分之五十左右，
对成本影响非常明显。

所以统计成本时不能只记总 token，必须把缓存命中 token 和未命中 token 分开记，
否则算出来的成本会偏高，看不出优化的效果。

## 按金额做配额而不是按次数

不同场景的单次成本差距很大。实测普通问答单次约零点零零一元，
而双工具的 Function Calling 单次约零点零零四四元，差四倍以上。

如果配额按调用次数限制，用户刷四次便宜问答和刷一次工具调用花费相当，
但次数配额完全拦不住。所以应该按金额累计做配额。

## 一个容易忽略的指标

首字延迟（TTFT）和总耗时是两个不同指标。用户感知最强的是首字延迟，
优化流式体验要盯这个数，而不是总时长。实测首字延迟在三百到四百毫秒。
